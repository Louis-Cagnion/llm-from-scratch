# IN15. Application security

| Track | Stage | Depends on | Needed by |
|---|---|---|---|
| Programming | 7. Cryptography, security and cloud | IN11, IN08, IN14, SY02 | none directly (used by L43 to L51, L67) |

## Why this module

The product side of the project is exposed: an API server with keys, a web chat that renders model output as HTML, artifacts that run JavaScript generated by the model, tools that read files and agents that execute code. Model output is untrusted input, and prompt injection can turn a helpful agent into an attacker. This module gives the security foundations every harness module relies on.

## Objectives

After this module, you can identify and prevent the common classes of vulnerabilities in a web application and a tool-using system, isolate untrusted code, protect secrets, and review code for security.

## Competences evaluated

1. Prevent injections: command injection, path traversal, and injection into interpreters, by validating and escaping inputs.
2. Prevent cross-site scripting by escaping output in the right context (HTML, attributes, JavaScript, URLs), and render untrusted Markdown safely.
3. Explain browser isolation (same-origin policy, iframe sandbox, Content Security Policy) and configure it for content that must run untrusted code.
4. Prevent cross-site request forgery on a local web application.
5. Implement authentication for an API (API keys, hashed storage, HMAC-signed tokens) and sessions for a web application.
6. Store and handle secrets correctly: never in code or logs, redaction of logs, rotation.
7. Explain why unsafe deserialization is dangerous and design safe formats.
8. Sandbox the execution of untrusted code with operating system mechanisms (separate processes, resource limits, Linux namespaces, seccomp) and apply least privilege.
9. Explain supply-chain risks and why the from-scratch policy reduces them.
10. Review code for security against known weakness classes (the CWE catalogue) and write a vulnerability report with severity and fix.

## Notions, in learning order

1. **Threat modeling**: assets, attackers, trust boundaries, untrusted input (including model output).
2. **Injections**: shell commands, file paths, templates, interpreters.
3. **Web vulnerabilities**: XSS (stored, reflected, DOM-based), CSRF, clickjacking, open redirects.
4. **Browser isolation**: origins, same-origin policy, iframes and their sandbox attribute, Content Security Policy, `postMessage` validation.
5. **Authentication and sessions**: API keys, password and key storage, signed tokens, cookie attributes.
6. **Secrets**: storage, environment variables, redaction, rotation.
7. **Deserialization**: why formats that execute code are dangerous.
8. **Sandboxing**: process isolation, resource limits, namespaces, seccomp filters, least privilege.
9. **Supply chain**: dependencies, updates, integrity.
10. **Security review**: CWE classes, checklists, reporting.

## Practice

- Attacking and then fixing a deliberately vulnerable local web application written for the exercise (injection, XSS, CSRF, path traversal).
- A sandbox that runs a Python snippet in a separate process with memory, time and file system restrictions, tested with escape attempts.
- A Markdown renderer (from IN12) hardened against XSS and tested with a list of malicious inputs.

## Evaluation format

One practical session, about 3 hours: find and fix vulnerabilities in code never seen before, configure the isolation of an untrusted page, write a security report, and answer questions on attack classes. Pass mark 100 %.
